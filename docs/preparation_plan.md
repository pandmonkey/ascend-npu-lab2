# 上机前准备计划

## 需要先问清楚的问题

这些问题不问清楚，后面很容易写出“本地看起来完整、上机完全跑不了”的代码。

1. 昇腾环境入口是什么：TensorOJ、学校远程服务器、华为云、还是本机 SSH 到裸机。
2. 芯片型号是否明确为 910B，以及是否允许固定使用单张卡、单个 AI Core。
3. 可用开发方式是什么：Ascend C、TIK、CANN 自定义算子、Python 封装、课程平台模板。
4. 是否能读取 cycle 级计时，或只能用 host 侧 wall time。
5. 是否有示例 microbenchmark 或课程指定模板。
6. 是否允许使用 inline assembly、特殊 intrinsic、硬件 event counter。
7. 编译运行限制：单次运行时长、内存上限、是否能保存原始数据文件。
8. 报告中是否允许标注部分参数为估算值，还是所有参数都必须实测。

## 工程准备

已经提前完成：

- `docs/benchmark_manifest.csv`：21 个参数清单、优先级、测量模式。
- `ubench/`：21 个参数的独立目录。
- `data/raw/measurements_template.csv`：原始测量数据字段模板。
- `scripts/summarize_results.py`：按参数聚合均值、标准差、最小值、最大值。
- `scripts/validate_project.py`：检查目录、manifest 和数据模板是否完整。
- `report/report.md`：报告骨架。

拿到环境后应立即补充：

- 顶层 `env.md`：记录卡型号、驱动、CANN、编译器、运行命令。
- 每个 `ubench/<id>_*/` 目录下的真实源码、构建脚本和运行脚本。
- `data/raw/measurements.csv`：真实原始数据。
- 图表生成脚本，建议后续放到 `scripts/plot_results.py`。

## 第一阶段：核心参数

先做 PDF 明确建议优先完成的 6 个参数：

| 参数 | 原因 | 最低可接受产物 |
| --- | --- | --- |
| S1 | 标量延迟基准，后续 S2/S3 可复用计时框架 | 依赖链代码、至少 10 次重复数据、均值/方差 |
| V1 | Vector 加法核心延迟 | 依赖链代码、至少 10 次重复数据 |
| V2 | Vector 乘法核心延迟 | 与 V1 对称，方便交叉验证 |
| C1 | Cube 最小 tile 延迟，是矩阵乘部分基础 | 单 tile matmul benchmark |
| M1 | L1 读带宽，MTE 核心参数 | 数据规模 sweep、带宽峰值 |
| M2 | L1 写带宽，MTE 核心参数 | 数据规模 sweep、带宽峰值 |

这 6 个跑通后，再扩展到同类参数。不要一开始平均铺开 21 个，否则很容易每个都半成品。

## 第二阶段：扩展参数

推荐顺序：

1. Vector：`V3`、`V4`、`V5`，因为能复用 `V1/V2` 的计时和向量指令框架。
2. MTE：`M3`、`M4`、`M5`、`M6`、`M7`、`M8`，因为能复用带宽 sweep 和 pointer chasing 思路。
3. Cube：`C2`、`C3`、`C4`、`C5`，因为 Cube 相关通常最依赖平台细节，晚一点做更稳。
4. Scalar：`S2`、`S3`，如果平台很难直接控制 Scalar Unit，这两项可能需要用可解释的估算方案。

## 数据纪律

每一次上机运行都要保留原始记录，至少包含：

- 参数编号
- benchmark 目录
- 设备型号
- CANN/驱动版本
- 问题规模
- 循环次数
- warmup 次数
- 重复编号
- 原始周期或原始时间
- 换算后的测量值
- 单位
- 备注

不要只在报告里放一个最终数字。这个作业报告质量和可辩护性很依赖原始数据。

## 风险判断

这个课题范围确实偏大。务实目标应该是：

1. 核心 6 项做到代码能跑、数据可信、报告解释清楚。
2. 其余 15 项尽量复用框架，优先保证“独立可运行”和“有原始数据”。
3. 对难以直接隔离的参数，报告里明确限制、误差来源和估算方法，不要写成绝对精确。
